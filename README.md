# AgentFabric

Reference implementation supporting the Maximus Industries AG Agent Fabric Strategy (Accenture B-School Challenge S10). Builds a shared orchestration and governance layer (the "Fabric") once, then plugs in two thin, function-specific agents — Finance (invoice processing) and Procurement (RFQ/quote comparison) — to demonstrate that the second agent is a configuration exercise on shared infrastructure, not a new integration project.

Status
 Phase 1 — Scaffold & mock data
 Phase 2 — Fabric core (shared tools + approval/audit layer)
 Phase 3 — Finance agent
 Phase 4 — Procurement agent
 Phase 5 — Demo script
 Wave 5 — Corporate agent (management reporting), added beyond the original 5-phase plan to prove the pattern scales to a third function
 Wave 3 — IT agent (service-management / ticket triage), added to show the contrast: the one wave that genuinely costs more to build (Section 7: €5–6M vs €2–3M) because it needs a new connector type, not just config

cp .env.example .env   # USE_LLM=false works with no API key

Run the fabric tests (Phase 2)
No external dependencies required — pure stdlib.

python3 tests/test_fabric.py
data/audit_log.json and data/escalation_queue.json are created on first write and are gitignored / not shipped pre-populated — they're regenerated by running the tests or the (future) demo.

Run the Finance agent tests (Phase 3)
python3 tests/test_finance_agent.py
Runs run_finance_agent() against all 8 mock invoices and checks the decision, reason content, audit log, and escalation queue. Works with USE_LLM=false (default) and zero API calls — no langgraph or anthropic package required to run this test, since run_finance_agent calls its five nodes directly in sequence.

A build_finance_graph() function is also provided in finance_agent.py for anyone who wants to run the same nodes through the actual LangGraph runtime (pip install langgraph required) — it's not used by the tests or the demo, just available.

Run the Procurement agent tests (Phase 4)
python3 tests/test_procurement_agent.py
Runs run_procurement_agent() against all 3 mock RFQs, plus re-runs the Finance batch first, then asserts the regression check that matters most: both finance_agent and procurement_agent records land in the same data/audit_log.json, and src/fabric/ was not modified to build this agent (verified separately via md5sum during development — Procurement added one new agent file and zero lines to fabric/).

Same USE_LLM=false, zero-dependency, zero-API-call pattern as Phase 3.

Run the demo
pip install -r requirements.txt
cp .env.example .env   # USE_LLM=false is fine, no key needed
python3 src/demo.py
Runs all 8 Finance invoices, all 3 Procurement RFQs, all 4 Corporate report requests, and all 4 IT tickets through their respective agents, prints one combined decision table (19 rows), and prints a "Shared Infrastructure Proof" block showing all four agents' records landing in the same data/audit_log.json.

This build deliberately spans the full cost spectrum from the strategy deck's Section 7 table, not just the cheap end:

Wave	Agent	fabric/erp_tools.py change	Why
1	Finance	(built erp_tools.py from scratch)	first agent, builds the shared layer
2	Procurement	zero new lines	reuses Finance's exact data shape — the cleanest proof of config-only reuse
5	Corporate	+3 functions (additive)	new entity type (report requests), but simple flat lookups
3	IT	+6 functions (additive)	new entity type AND correlates two related tables (ticket + source system + known-issue library) — the one wave needing a genuinely new connector type, matching the deck's claim that IT is the only wave costing more to build than Procurement
fabric/approval_tool.py — the actual governance layer (audit log + escalation queue) — stayed 100% byte-identical across all four agents, confirmed via diff at each step. That file is the real "shared infrastructure" claim; erp_tools.py growing additively per new data domain is expected and doesn't undercut it.

Uses rich for formatted tables/panels if installed, and falls back to plain-text output automatically if rich isn't available — either way the demo runs to completion with USE_LLM=false and zero API calls.
